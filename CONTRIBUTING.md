# Contributing to Focale releases

Thanks for helping improve Focale's distribution. Reports of broken downloads,
installation or update problems, documentation improvements and focused workflow
fixes are welcome.

GetFocale is the public distribution repository. Downloads are presented on
[Focale's main website](https://focale-editor.app/#downloads); this repository
provides release files and the metadata used by the website and desktop updater.

## Reporting a problem

Search [Focale Community issues](https://github.com/focale-editor/community/issues)
before opening a [bug report](https://github.com/focale-editor/community/issues/new?template=01-bug-report.yml).
For a download, installation or update problem, include:

- your operating system, its version and processor architecture;
- the Focale version, including its build number when available;
- the release, download URL or filename involved;
- steps to reproduce, the expected result and what happened;
- the exact error message and relevant logs or screenshots.

For update problems, include both the installed version and the offered version.
Remove credentials, personal information and private project contents from
attachments. Editor bugs, feature requests, improvements and questions also
belong in Focale Community, which centralizes user feedback across the project.

## Working on the repository

Fork the repository and create a focused branch from `main`:

```sh
git clone https://github.com/YOUR_ACCOUNT/releases.git
cd releases
git switch -c docs/short-description
```

This is a static repository: no Dart, Flutter or Node.js dependencies are needed
to edit its documentation or Pages files.

| Path                                      | Purpose                                                     |
|-------------------------------------------|-------------------------------------------------------------|
| `README.md` and `CONTRIBUTING.md`         | Public documentation                                        |
| `.github/workflows/build.yml` | Compiles pinned private release sources on public runners |
| `.github/workflows/notify-build.yml` | Resumes private publication after successful builds |
| `tool/ci/` | Validates source identities and publication callbacks |
| `.github/workflows/pages.yml`             | Deploys `site/` to GitHub Pages                             |
| `site/index.html`                         | Redirects visitors to downloads on the main website         |
| `site/CNAME`                              | Custom distribution domain                                  |
| `site/downloads.json`                     | Generated catalog consumed by the main website              |
| `site/<target>/app-archive.json`          | Generated, signed update index for a platform and processor |
| `site/<target>/releases/<version+build>/` | Generated versioned descriptors and release notes           |

Target and version directories appear as releases are published. Application
archives and installers are attached to GitHub Releases.

## Making changes

Keep each pull request focused on one problem. Discuss changes to distribution
domains, metadata formats, supported architectures or update behavior with a
maintainer first: existing installations and the main website depend on these
contracts.

Release metadata is generated by the application's release pipeline. Report
incorrect entries rather than editing catalogs, signed indexes or versioned
descriptors by hand. Published assets and versioned metadata are immutable;
editing signed content also invalidates its signature. Maintainers handle fixes
through the release tooling.

Versioning and changelogs are managed through `dart run release` in the application
repository. Contribution pull requests here should not create application tags,
replace release attachments or publish new versions.

## Checking your changes

For documentation, check Markdown formatting, relative links and the accuracy of
paths and commands. Run:

```sh
git diff --check
```

For Pages workflow changes, also run
`actionlint .github/workflows/pages.yml`. If its runner registry does not yet
recognize a new GitHub-hosted image, verify the label against GitHub's supported
images and explain that limitation in the pull request.

To preview static files locally with Python 3:

```sh
python3 -m http.server 8000 --directory site
```

Use `python` instead of `python3` if that is your Python 3 command. The root page
redirects to the main website; individual files can be inspected directly, for
example at `http://localhost:8000/downloads.json`. Local preview does not validate
the production domain, signatures or an actual application update.

## Pull requests

Open your pull request against `main`. Explain the problem and resulting behavior,
link the related issue with `Fixes focale-editor/community#123` when applicable,
and describe the checks you ran. For installation or update reports, distinguish the platforms you tested
from those you have not exercised.

Use a descriptive title with a Conventional Commits prefix, such as
`docs: clarify Linux installation`, `fix: correct the download redirect` or
`ci: update the Pages runner`. Keep review follow-up commits on the same branch.

Build workflow changes also require `python3 -m unittest tool.ci.build_identity_test`
and `actionlint .github/workflows/build.yml .github/workflows/notify-build.yml`.
See [maintainer setup](docs/builds.md) for the protected environment and token scopes.
